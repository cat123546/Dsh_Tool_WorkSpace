# 工作区框架评审报告

> 评审对象：结构框架.txt + 7 份 AGENTS.md/索引 + 初始化指令
> 评审依据：本机 DSH 0.2.x（desktop profile）实际源码与行为，非通用推测

---

## 一、总体结论

**骨架是对的，可以直接用；但有 3 个"会让它悄悄失效"的前提没处理，2 个设计需要改，1 个理解需要纠正。**

| 维度 | 评价 |
| :--- | :--- |
| 六条总原则 | 5 条成立，第 5 条（省 token 靠静态）方向对但归因偏了 |
| 目录结构 | 合理，缺版本控制与回收站 |
| 分层 AGENTS.md | 结构对，但**当前会断链**（见 2.1），且分成 6 份属于过度设计 |

| token 控制 | 优化错了地方（见 三） |
| 初始化指令 | 可用，但自包含性和污染风险要处理（见 2.3） |

## 二、必须修的 3 个致命前提

### 2.1 没有 `.git` → 分层规则链会断（最严重）

DSH 加载 AGENTS.md 的真实规则（读源码 `dsh-agent-instructions/src/files.ts` 确认）：

- 项目根 = **从 cwd 向上找到的第一个含 `.git` 的目录**；
- 一路向上都没有 `.git` 时，**项目根 = cwd**（不是磁盘根）；
- 然后从项目根到 cwd 的**每一层**加载 AGENTS.md。

推论（这就是漏洞）：

| 场景 | 实际加载 | 后果 |
| :--- | :--- | :--- |
| cwd = `D:\DSH_WorkSpace`，无 `.git` | 只有根 AGENTS.md | 正常 |
| 会话切到 `D:\DSH_WorkSpace\输出结果`（用 cd 工具或某任务切换） | **只有 输出结果/AGENTS.md** | 根 AGENTS.md 整份丢失："输入资料只读"等硬约束全部失效 |
| 以后给 `项目A` 单独 `git init`，cwd 进入项目A | 只有 `项目A/AGENTS.md` | 同上，工作区基线消失 |

这不是理论风险：你自己的根 AGENTS.md 里写了"处理正式项目时，先读该项目的 AGENTS.md"——一旦那个项目有独立 `.git`，它的上层规则就不在链上了。

**修法：在工作区根放一个 `.git` 标记**，让项目根钉死在 `D:\DSH_WorkSpace`，整棵树始终是一条链。

注意本机**没有安装 git**，所以不要写成"跑 git init"。好消息是加载器只探测 `.git` 这个路径**是否存在**（源码 `existsAsMarker` 只做存在性检查），不校验它是不是有效仓库。所以有两个零依赖选项：

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| A（立刻可用） | 在工作区根建一个空的 `.git\` 目录 | 语义脏；以后装了 git 直接 `git init` 会被正常接管，不冲突 |
| B（更干净） | 在 profile 的 `cordis.patch.yml` 里给 agent-instructions 配 `projectRootMarkers: ['.git', '.dsh-root']`，然后放一个 `.dsh-root` 空文件 | 要改一次 profile 配置（不是写插件），并确认 patch 生效 |

钉住项目根还顺带带来两个好处：

1. 项目级 skill（`.dsh/skills/`）和 AGENTS.md 用同一个项目根，行为一致；
2. 以后任何"按目录生效"的机制都不会因为 cwd 变化而漂移。

至于**版本控制 / 删除后悔药**：本机没 git，就别把它当基础假设。替代方案是 `_trash/YYYYMMDD/` 缓冲（见 Q3 第 4 条），加上可选的"输入资料哈希清单"（见 4.3）。

### 2.2 权威顺序自相矛盾

原文：

> 系统提示词 > 用户直接指令 > 本文件 > 子目录 AGENTS.md。冲突时以更具体目录的规则为准。

同一句话里先说"本文件 > 子目录"，又说"更具体的优先"，agent 读到会随机选一个解释。

DSH 注入时的官方措辞是：*"More specific instructions take precedence over broader ones. They do not override system, developer, or direct user instructions."*

**改成唯一顺序：**

```
系统/开发者指令 与 用户当前指令  >  子目录 AGENTS.md  >  根 AGENTS.md
同层冲突时，后写入的、更具体的那条为准。
```

### 2.3 初始化指令会污染下载目录

指令最后写"删除本文件（初始化指令.md）"——如果 agent 在 `Downloads/` 里执行，删掉的是**你下载的原始文件**，而不是工作区里的副本；而且 9 份规格分散在 Downloads，指令本身不自包含（里面写"按 X 规格写入"，agent 必须反向去读 Downloads 里另外几个 md）。

**修法：** 初始化指令 + 全部规格合成**一个自包含文件**放进工作区（如 `_init/初始化.md`），执行完删除 `_init/`。这样：只需读 1 个文件、不会误删、可重复执行。

## 三、你问的三个问题

### Q1：AGENTS.md 会不会被反复读取、白烧 token？

**不会。** 机制（来自 `dsh-agent-instructions` README + 源码）：

- 基线**每个会话只在第一次请求注入一次**，是一条持久 user 消息，之后一直在历史里，不会每轮重读；
- 之后只有"成功的 read/write/edit **触达了新目录**"时，才追加一条新增指令块（一次）；
- **路径和内容摘要都没变的内容，绝不重复注入**；
- 子目录 AGENTS.md 不是启动就载，是"你第一次碰到那个目录时才载"——这本身就是按需加载。

真正会额外产生 token 的只有 4 种情况：

1. 文件**内容变了** → 追加一条 `Updated instructions from:` 替换块（旧内容仍留在历史里，等于双份）；
2. 文件被删除 → 追加一条移除通知；
3. 超出预算（默认 64 KB/链）→ 追加预算警告；
4. **每开一个新会话** → 重新注入一次（不可避免，也是设计意图）。

所以你的"静态性"原则**方向完全正确**，但它的真正价值是**避免第 1 条的重复注入和缓存失效**，而不是"防止每轮重读"——后者本来就不会发生。

**量级参考：** 你现有 7 份文档合计 **4228 字节**，约 1000 token。一次性注入，占一次正常会话总消耗的 1% 以下。**AGENTS.md 不是你 token 消耗的大头**，优化它收益极小。

### Q2：token 到底掉在哪？怎么省？

真实的大头，按影响排序：

| 排序 | 消耗源 | 典型量级 | 对策 |
| :--- | :--- | :--- | :--- |
| 1 | **长会话历史每轮全量重发** | 每轮都是全部历史 | 一个任务一个会话；超长就压缩/收尾 |
| 2 | **探索**：反复 glob/grep/read 试错 | 单次扫全仓可上千 token | 一条命令先拿目录清单；大文件先 grep 行号再 read 片段 |
| 3 | **工具输出**（哪怕截断到尾部） | 一次几百到几千 token | 命令里就做过滤/统计，别把原始内容倒出来 |
| 4 | **失败重试**（路径错、沙箱拒、命令不兼容） | 每次都是完整往返 | 一次确认环境变量、用对 shell 语法 |
| 5 | 探索型任务自己做 | 每条线索一次往返 | 交给子代理，只回结论 |
| 6 | AGENTS.md | ~1000 token/会话 | 已经很小，别过度优化 |

**现场示范：** 这次评审里"调研开源做法"那步我交给了子代理，它内部搜索/抓网页烧掉的 token 不进我的上下文，只回来 1200 字结论。这是 DSH 里收益最大的省 token 手段，建议固化进规则：

> 凡是"帮我找出所有…""排查为什么…""这个仓库里哪些…"这类**需要多轮搜索**的任务，默认交给子代理，只回结论。

另外三个 DSH 原生动作值得写进规则：

- 一条命令替代多次调用（`Get-ChildItem -Recurse | Select Name,Length,LastWriteTime`）；
- 独立操作并行发起（同一条消息里多个工具调用）；
- 大文件 `grep 定位 → read offset/limit`，绝不整读。

### Q3：手动盘点清理，可行吗？

**思路可行（低频、人工确认、agent 只给信息，这个架构是对的），但你给的实现方式成本会失控，而且判定标准是不可靠的。**

问题在于这步：

> Agent 根据 AGENTS.md 中的分类标准（临时过程/不确定），列出候选清单并附一句话理由。

要让 agent 判断"这是临时过程还是不确定"，它必须**读内容**。`_scratch/` 攒 30 个目录时，一次盘点可能几十次工具调用、上万 token——正好是你最想省的地方。而且"临时/不确定"是语义判断，两次盘点结论可能不一致。

**改法：把"语义判断"降级成"元数据判断"。**

1. **`_scratch/` 用日期前缀命名：`20261120-简称/`**
   理由：目录名自带新旧信息，盘点时一条命令就能排序，不用看 mtime、不用读内容。
   （`输出结果/` 保持不加日期是对的——它靠 HISTORY.md 索引，日期会造成重名和"日期≠内容"的误读。两个区不同策略，不冲突。）

2. **每个临时实验目录必须有一个 `README.md`，前两行固定格式：**

   ```
   status: active | done | abandoned
   用途: 一句话
   ```

   盘点时只读这些两行标记，不读其余内容。`done` / `abandoned` 直接就是候选。

3. **盘点 = 一条命令 + 一张表**，不遍历、不读正文：

   ```
   目录名 | 最后修改 | 大小 | status | 建议（删除/归档到输出结果/升格到_toolbox/保留）
   ```

4. **"不删除"保留，"不移动"可以放宽。**
   你写"系统不执行任何移动/删除操作"。不删除是对的（不可逆）；但**不许移动**是多余的严格——移到 `_trash/20261120/` 是可逆的，而且比让你手动点几十次强。
   折中建议：**agent 默认只出清单 + 附一条可直接执行的命令**；你审阅后一键运行。既保留人的决定权，又把执行的摩擦降到一次操作。配合 git，删错了能恢复。

5. **从源头减少垃圾**（比事后清理更省）：`_scratch/` 下禁止直接放文件、必须建任务目录（你已经有这条，很好）；再加一条"实验结束当场写 status，不留悬案"。

**成本对比：**

| 方案 | 30 个目录的盘点成本 | 判定稳定性 |
| :--- | :--- | :--- |
| 你现在的方式（读内容判断） | 约 30 次读取，上万 token | 低，每次结论可能不同 |
| 元数据 + status 标记 | 1–2 次命令，几百 token | 高，纯机械规则 |

## 四、其他缺陷（按严重度）

### 重要

**4.1 6 份 AGENTS.md 是过度设计。**
全部规则合计 4.2 KB，而 DSH 预算 64 KB/链。分层真正的价值是"规则量大到不能常驻时按需挂载"，你现在远没到那个量级。分成 6 份的代价却真实存在：

- 每次任务多 1–2 次 read 调用（你自己的"路由"就在指示 agent 先读两份）；
- 子目录规则要等 agent 触达才生效——**第一次写入时规则还没被看见**（注入发生在那一步之后），等于约束滞后一步；
- 断链风险（见 2.1）；
- 改一条规则要在 3 个文件里保持一致。

**建议：根 AGENTS.md 内联全部高频硬约束 + 目录职责 + 命名模板（约 60–80 行）；只给 `_toolbox/` 和"项目模板"保留子文件**（这两处规则又长又低频）。`输入资料/`、`输出结果/`、`_scratch/` 的 AGENTS.md 可以删掉，规则并入根。

判据：**一条规则如果每次任务都要用，就必须在根；只有"涉及某目录才用"的才下沉。** 你现在 `输入资料/AGENTS.md` 的核心内容（只读、产物写输出结果）恰恰是每次都用的，放子目录反而最亏。

**4.2 `_Toolbox` 的提取门槛里有两条无法验证。**
"被使用/调用至少 2 次"——agent 怎么查证？"维护成本低于重写成本"——纯主观。不可验证的判据等于没有判据。

**改成可观测的：**

| 现状 | 建议 |
| :--- | :--- |
| 被使用 ≥2 次 | 能被 grep 证明在 ≥2 个目录里出现过同类逻辑；或本次任务明确预见复用 |
| 成本低于重写 | 删掉，换成硬条件：有 `--help`、依赖写在目录内 `README.md`、无绝对路径 |
| 模块化合格 | 保留，再加"固定入口 + 依赖清单 + 一个可跑示例" |
| （缺） | 一个工具一个目录，目录内 `README.md` + 入口脚本 + 依赖文件 |

**4.3 没有版本控制 = 手动删除没有后悔药。**
你打算"自己直接删除"，那删除就是不可逆的。这是整个方案里风险最高的一步。本机没有 git，两个低成本替代：

- **删除缓冲**：任何删除先进 `_trash/YYYYMMDD/`，隔一段时间再清空。一次 `Move-Item` 的代价，可逆。
- **只读校验清单**：给 `输入资料/` 生成一份哈希清单，盘点时比对，能发现"被改过/被动过"。

  ```powershell
  # 建立基线（放好资料后跑一次）
  Get-ChildItem '输入资料' -Recurse -File | Get-FileHash -Algorithm SHA256 |
    Select-Object Path,Hash | Export-Csv '.meta\输入资料-hashes.csv' -NoTypeInformation
  # 校验（与基线比对，无输出=没人动过）
  $old = Import-Csv '.meta\输入资料-hashes.csv'
  $new = Get-ChildItem '输入资料' -Recurse -File | Get-FileHash -Algorithm SHA256 | Select-Object Path,Hash
  Compare-Object $old $new -Property Path,Hash
  ```

  这个方案顺带解决了"只读无从验证"的问题，且完全不需要 git。

**4.4 索引文件的维护成本被低估。**
每次归档都要更新 `HISTORY.md`。如果 agent 先 read 再 edit，是两次往返；用一条 `Add-Content` 是 1 次。建议在规则里直接给命令，并规定索引**只追加、表格一行一条、字段固定**，永不要重写整表。

### 可选

**4.5 目录命名不一致。** `_Toolbox`（大写T）、`_scratch`（小写）、`项目A-数据清洗`（中文+字母）。建议统一：下划线区全小写（`_toolbox`、`_scratch`），或都大驼峰。可预测性比美观重要。

注：Windows 下 `_` 的排序在字母**之后**，不会像你想的那样排在最前。想置顶用 `0_` 或中文。

**4.6 项目模板太薄。** 12 行里 6 行是空的字段名。建议补：一个填好的示例、一行"本项目禁止事项"、一行"产物出口路径"。

**4.7 缺少"收尾清单"。** 现在没有任何一步要求"任务结束时确认文件归位、索引更新、给出一句话说明"。加 3 行，能消掉大部分后续整理工作。

**4.8 缺少"不得自行修改规则"的约束。** agent 完全有可能"顺手优化"AGENTS.md。规则文档被 agent 改是隐性风险，建议明写：只提建议，不直接改。

**4.9 输入资料只读缺可操作定义。** "不修改"对 agent 太抽象。建议列白名单/黑名单操作：允许 read/glob/grep；禁止 write/edit/删除/重命名/移动，以及任何 shell 重定向写入该目录。

## 五、建议的改进版结构

```
D:\DSH_WorkSpace\
├── .git/                      ← 新增：空目录即可，作用是钉住项目根（不是 git 仓库）
├── .gitignore                 ← 可选：以后装了 git 才有用
├── AGENTS.md                  ← 唯一常驻规则（约 70 行，内联全部高频约束）
├── README.md                  ← 给人看的工作区说明
├── 输入资料/                   ← 无 AGENTS.md，规则在根
├── 输出结果/
│   ├── HISTORY.md             ← 一行一条，只追加
│   └── <任务简称>/
├── <项目>-<简称>/              ← 项目内独立 AGENTS.md
├── _toolbox/
│   ├── AGENTS.md              ← 保留（提取门槛，低频长规则）
│   ├── INDEX.md
│   └── <工具名>/               ← 一工具一目录：README.md + 脚本 + 依赖
├── _scratch/                  ← 无 AGENTS.md，规则在根
│   └── 20261120-<简称>/
│       └── README.md          ← status: / 用途:  两行
└── _trash/                    ← 可选：待删缓冲区
```

根 AGENTS.md 建议内容（可直接用）：

```markdown
# 工作区基线

## 权威顺序
系统/开发者指令 与 用户当前指令 > 子目录 AGENTS.md > 本文件。
冲突时以更具体的规则为准。

## 目录职责
| 目录 | 放什么 | 约束 |
|---|---|---|
| 输入资料/ | 原始材料 | 只读：允许 read/glob/grep；禁止 write/edit/删除/重命名/移动，禁止重定向写入 |
| 输出结果/ | 非项目任务的成品 | 按任务建子目录，登记 HISTORY.md |
| <项目>-<简称>/ | 长期维护的项目 | 遵守该项目 AGENTS.md |
| _toolbox/ | 跨项目工具 | 满足 _toolbox/AGENTS.md 门槛 |
| _scratch/ | 一次性试验 | 建 20261120-简称/ 子目录，写 status 两行 |

## 产出归属（按顺序判定）
1. 要长期维护、会反复改 → 项目目录
2. 一次性交付、事后要能找到 → 输出结果/<任务简称>/
3. 只是过程、无交付价值 → _scratch/YYYYMMDD-<简称>/
4. 不确定 → _scratch/，并在回复里说明原因

## 命名模板
- 任务子目录：2–6 个汉字，不含日期、版本号
- 输出文件：<任务简称>-<内容>.扩展名；同一任务产物 ≤8 个
- 临时实验：YYYYMMDD-<简称>/
- 禁用名：新建文件夹、test、temp、副本、最终版、最新

## 硬约束
- 输入资料/ 只读（定义见上表）
- 根目录只放 AGENTS.md、README.md、.gitignore 与固定目录，不放任务文件
- 目录嵌套不超过 2 层
- 不直接修改任何 AGENTS.md；需要改就提建议，等人确认

## 检索纪律（省 token）
- 先一条命令拿目录清单（名字/大小/时间），再决定读什么
- 大文件先 grep 定位行号，再 read offset/limit 读片段
- 相互独立的操作在同一步并行发起
```

## 六、可借鉴的开源做法（对照表）

| 来源 | 精华 | 用在哪 |
| :--- | :--- | :--- |
| AGENTS.md 标准 | 只写"你会告诉新同事的事"；**能从代码/目录推断的一律删** | 你的"路由"可砍一半 |
| Claude Code memory | 子目录文件**按需加载**；单文件 <200 行；`/doctor` 主动裁掉目录清单、依赖列表、架构概述 | 支持你精简根文件 |
| Anthropic 上下文工程 | **最小的高信号 token 集**，不是最短文本；长流程外置成 skill；子代理隔离 | 盘点流程做成可按需加载的文档 |
| Aider repo map | 用**索引+签名**代替盲目探索，明确 token 预算（默认 1k） | 你的 INDEX.md 思路同源，可以更明确地定预算 |
| Cursor / Cline rules | 每条规则带"适用范围 + 触发条件"元数据，**不要全部常驻** | 你未来的 `.dsh/skills/` 可挂条件规则 |
| spec-kit | 稳定层（constitution）与每特性过程产物**分目录、独立编号** | 你的 输出结果/ 归档区同构，可引入编号 |

一条值得单独说的：**DSH 自带 skill 机制，用它可以零插件实现"按需加载的长流程"**。把"盘点清理"写成 `.dsh/skills/cleanup-audit/SKILL.md`，平时在目录里只占一行描述（约 15 token），你说"盘点"时才加载全文。这正好是"低频、手动触发"的最佳载体，且不需要写任何插件代码。

（注意：skill 的项目根同样依赖 `.git`——又一次回到 2.1。）

## 七、落地顺序（建议）

1. 建 `.git/` 空目录钉住项目根（其余一切都依赖它）——先做；
2. 单份根 AGENTS.md（把 6 份的内容合并进去，删掉 输入资料/、输出结果/、_scratch/ 的）；
3. 保留 `_toolbox/AGENTS.md`（按 4.2 改写门槛）与项目模板；
4. 建目录骨架 + 两个索引文件 + `_trash/`；
5. 约定 `_scratch/YYYYMMDD-简称/README.md` 的两行 status；
6. 可选：把"盘点"做成 `.dsh/skills/cleanup-audit/`；
7. 手工验收：新开一个会话，确认根规则被加载、输入资料能被读到、输出结果写入路径正确。特别注意验收"把 cwd 切到子目录后根规则是否还在"——这是最容易漏测的一条。
